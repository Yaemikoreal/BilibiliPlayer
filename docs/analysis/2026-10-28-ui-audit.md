# B站分身控制台 · UI/UX 审计与信息架构改造方案（2026-10-28）

> **性质**：只读审计。本文件是唯一产出，**没有改任何代码**，没有提交。
> **对象**：`dsh-plugin/client.js`（**181,672 B / 2,897 行**；本文件所有"现状"行号以该版本为准，取自 2026-10-28 00:1x 的磁盘版本）。
> **输入**：`dsh-plugin/CONSOLE-DESIGN.md`、`docs/analysis/2026-10-27-dsh-ui-conformance.md`（下称**规范稿**）、`docs/analysis/2026-10-26-console-ui-v3-design.md`、`dsh-plugin/test/client.render-smoke.mjs`，以及 asar 内 4 个宿主源码锚点（见 §1.2）。
> **验收目标（用户原话）**：
> ① "UI 不适配 dsh，不美观也并不贴合 dsh 本身设计风格"；
> ② "现在的插件页面有些过于杂乱，布局混乱，让人看不到主体和关键信息"。
> **不在本审计范围**：概览页"不实时"的**数据侧**根因（另一名同事负责）、"没主动回复别人评论"的**行为侧**根因（另一名同事负责）。本文件只在 UI 侧指出这两个症状的**可观测表现**（§2.1-A7、§2.2-B5、§2.4-D10）。

## 0. 结论摘要（给 Lead 的 8 条）

1. **底座已经对齐宿主，问题不在 token，而在结构与层级。** 页面容器 960/clamp/28/48（`client.js:540`）、下划线页签几何（`:548–553`）、按钮族 32/28+12/8+l3+`.4`（`:182–201`）、开关 36×20/位移 16（`:204–215`）、pill 24/无边框/layer-2（`:171–175`）、`corner-shape:round`（`:115`）、`prefers-reduced-motion`（`:116`）、`--dsw-*` 映射层（`:59–102`）**都已合规**。清单见附录 B。**不要重写这套 CSS 变量，不要重做主题。**
2. **"看不到主体"的第一原因是概览页 7 张同权卡片 + 顶部状态行与"值班状态"卡重复 4 个事实。** 概览返回 7 张卡（`client.js:1461–1475`），全部 `.bf-card` 同材质同 14px 标题；而"自动值班/下一轮/运行中/上轮退出码"在 `.bf-status-row`（`:2792–2797`）与 dutyCard（`:1337–1342`）各写一遍。
3. **7 个页面都没有页头。** 静态结构里唯一的 `<h1>` 是全局的"B站分身"（`:2782`；日报正文的 `<h1>` 来自 Markdown 渲染，`.bf-md h1` `:636`，不是页面标题）。切到活动/日报/判重/设置后，正文直接是控件或卡片流，用户不知道"这一页回答什么"。宿主每个插件页都有 `pageTitle 20/500/28 + pageIntro 13/20 secondary`（宿主 S3，plugin-manager:1913）。
4. **"今天做了什么、说了什么"没有任何一处聚合。** 今日轮次只以 `roundsToday + ' 轮'` 藏在 dutyCard 倒数第二行（`:1342`）；今日评论数**完全不存在**（`presenceFrom` 只算 7 天，`:1254–1284`）；"它说了什么"最多只有 1 条（`presence.latest`，`:1398–1402`）。
5. **三个可直接改的硬 bug**（不是设计问题，是写错了）：① `.bf-card-foot` 在 `:1343`、`:1366` 使用，但 STYLE 里**没有这条规则** → 卡脚三个按钮无间距、无分隔线；② `.mono` 在 `:2009/:2010/:2666/:2667/:2678` 使用，CSS 里只有 `.bf-mono`（`:313`）→ 判重表日期/版本名根本没等宽；③ 6 个配额瓦片塞进 5 列的 `.bf-grid-5`（`:557`/`:1464`）→ 宽屏下第二行留 1 个孤儿瓦片。
6. **人设页是全控制台最杂的一页**：首屏 17 个可交互元素（4 个 chip + 3–4 个预设按钮 + 刷新 + 状态 pill + 8 个子页签），且 4 个轮询 hook 在卡片页签上也会全量拉（`:2243–2246`）。
7. **"不实时/卡"的 UI 侧一半原因**：`ConsolePage` 无条件常驻 5 个轮询（`:2726–2731`：3s/3s~15s/60s/30s/SSE 或 1s~5s），`usePoll` 只在 `document.hidden` 时暂停（`:742`），换页签不暂停；且 `usePoll` 不记录 `lastUpdated`（`:720–754`）→ UI 无法显示"12 秒前刷新"，只能在页脚写一句"概览每 3s 刷新"（`:1473–1474`）。
8. **信息架构建议 7 → 5 个页签**：概览（吸收"实时"的运行态）、活动（吸收"判重表"为第三视图）、日报、人设（8 子页签 → 3）、设置（2 子页签 → 3）。详见 §3。

## 3. B · 信息架构提案

### 3.1 一句话判断

用户每天只想知道四件事，**按这个顺序**：

1. **在跑吗？**（自动值班开没开、下一轮什么时候、现在是不是正在跑）
2. **今天做了什么？**（几轮、挑几个、评几条、赞几个）
3. **它说了什么？**（评论原文，以及有没有人回它）
4. **有没有毛病？**（凭证 / CLI / 模型 / 家目录）

现在这四件事散在 **4 个页签 + 7 张同权卡片**里，而 7 个页签里至少 2 个（实时、判重表）日常根本不用。

### 3.2 7 → 5

| 现页签 | 建议 | 理由（决定性理由，不是"也许"） |
|---|---|---|
| 概览 | **保留并重排**，吸收「实时」的运行态 | 用户每天来这里；但要从"状态机细节"改成"今天的结论" |
| 实时 | **删除独立页签**，并入概览 | 一天最多看 1–2 次，且只在"正在跑"的几分钟里有用；空闲时它是一张空卡（A7）。它本质是"运行中"这个状态的**详情**，天然属于概览 |
| 活动 · 生命周期 | **保留**，改名「活动」；吸收「判重表」为第 3 视图 | 三者都在回答同一个问题："它到底干了什么" |
| 日报 | **保留** | 文档型产物，与活动页不同介质，合并反而不自然 |
| 判重表 | **删除独立页签**，变成「活动」的第 3 个视图 | 纯审计视图（append-only 的 seen.md），日常不需要；但排查"它为什么重复看/为什么没看"时必须能到 |
| 人设工作室 | **保留为「人设」**，8 子页签 → **3** | 人设决定"它说什么"，属运营面而非偏好面，值得一级入口；但 8 个子页签是杂乱的直接来源 |
| 设置 | **保留**，2 子页签 → **3** | 30 个字段一屏到底（B7）无法扫读 |

**结果：概览 / 活动 / 日报 / 人设 / 设置 —— 5 个页签，宽度约 320px，一屏放得下且留白充分。**

> **保守变体（若 Lead 不愿动 live 的渲染冒烟）**：保留「运行」为第 6 个页签（6 个页签 / 约 380px），只做"判重表并入活动 + 人设 8→3 + 概览重排"。代价：首屏页头多一个页签，且"运行"页空闲态仍需按 §4.10 改成"上一轮复盘"，否则仍是一张空页。两版对 smoke 的破坏面差异见 §6.1。
