## 1. 角色卡数据模型

### 1.1 V2 字段表【规范原文】

V2 的实质变化：把 V1 的 6 个字段整体塞进 `data`，再加「元数据 + 覆写 + 内嵌世界书」三类。原文 TS 定义见参考 [1]。

| 字段 | 负责什么 | 进 prompt？ |
|---|---|---|
| `spec` / `spec_version` | 格式标识 `'chara_card_v2'` / `'2.0'`，**MUST** | 否 |
| `name` | 角色名。文档：**唯一必填字段**，其余可空 | 是（常驻） |
| `description` | 身份/外貌/背景/世界设定。原文："always included in the prompt, so all important facts should be included here"；可 200–2000 token，格式任意 | 是（常驻） |
| `personality` | 性格摘要 | 是（常驻） |
| `scenario` | 对话所处情境 | 是（常驻） |
| `first_mes` | 开场白。原文：模型**最容易从 first message 学到风格与长度**，胜过任何其他字段 | 仅开局一次 |
| `mes_example` | 示例对话，`<START>` 分块；**仅当 context 有余量时插入，超预算逐块挤出** | 动态/可挤出 |
| `creator_notes` | 给使用者看的说明，**MUST NOT 进 prompt** | 否 |
| `system_prompt` | 卡级 main prompt 覆写，支持 `{{original}}` 插回全局值 | 是（system 位） |
| `post_history_instructions` | 卡级 ujb/jailbreak 覆写 | 是（历史之后） |
| `alternate_greetings` | 备选开场白，前端 **MUST** 做成 swipe；群聊随机抽一条 | 仅开局 |
| `character_book` | 卡内嵌 lorebook；**SHOULD 与用户世界书叠加，且卡书优先** | 视触发 |
| `tags` | 检索分类，**SHOULD NOT 进 prompt** | 否 |
| `creator` / `character_version` | 作者名 / 卡版本，**MUST NOT 进 prompt** | 否 |
| `extensions` | 任意 KV，**MUST 默认 `{}`**，前端 **MUST NOT** 丢弃未知键 | 否（前端私有） |

> **关键设计信号**：V2 用「MUST NOT 用于 prompt」把**元数据**与**人设内容**硬隔离——「给人看的」与「给模型看的」应是两套数据。

## 2. 提示词编排与注入位置

### 2.1 槽位地图（拼接顺序）

酒馆给每个可注入物一个**命名槽位**；把文档的槽位枚举从上到下排，即为事实顺序：

| # | 槽位 | 放什么 | 影响强度 |
|---|---|---|---|
| 1 | System / Main Prompt | 全局行为准则；可被卡 `system_prompt` 覆写（`{{original}}`） | 基线，最易被稀释 |
| 2 | WI · **Before Char Defs** | 世界设定、背景常识 | 原文："moderate impact" |
| 3 | **角色定义区**：Description + Personality + Scenario | 「这人是谁」 | 常驻，永不挤出 |
| 4 | WI · **After Char Defs** | 强化设定、口吻提醒 | 原文："greater impact" |
| 5 | **Author's Note**（After Scenario 放置） | 格式/风格/当下状态 | 依位置而定 |
| 6 | **示例对话** `mes_example`（含 WI 的 Before/After Example Messages 槽） | few-shot 语气对齐；WI 条目可被当作示例块解析 | 有余量才插，逐块挤出 |
| 8 | **对话历史**（含 `@D` 注入、卡内 Character's Note、in-chat A/N） | 多轮上下文 | 越靠下越强 |
| 9 | **post_history_instructions**（ujb 位） | 最后裁决：格式、禁令 | 最强 |
【规范原文】常驻四件套＝**Name / Description / Personality / Scenario**；`first_mes` 只在开局发一次；`mes_example` 被填满后**逐块**（`<START>` 分隔）挤出，可强制保留。推论：示例**排序有稳定收益**——最重要的放最后一块，它活得最久。

### 2.2 depth / position 语义：为什么能压过写在开头的规则

**【规范原文】**（Author's Note 文档 [4]，depth 的权威定义）：

- `Depth 0` ＝放在**对话历史的最末尾**
- `Depth 4` ＝放在**最近 3 条历史之前**，成为历史中的第 4 个实体
- 原文结论：**"The closer the Author's Note is to the bottom of the prompt, the more impact it has on the next AI response."**
- 注入 role 可选 **user / system / assistant**

**【规范原文】**WI 的 `@D` 同义："插入到对话的特定深度（**Depth 0 是 prompt 底部**）"，同样可选三种 role。

**为什么「写在最后」能压过「写在开头」**【社区共识 + 个人经验，机制为推断】：

1. **近因效应**：模型对紧邻生成点的 token 条件最强；末尾指令参与「当前这一步」的分布，开头指令参与「整段」的先验。
2. **角色伪装**：`@D` 可用 **user 角色**注入，等于「用户刚刚补了一句」，比 system 规则更像**当前任务约束**——这正是「越狱位」存在的原因。
3. **不随历史漂移**：开头在长上下文里被平均稀释，末尾永远贴在窗口末端；历史越长，差距越大。

**边界（易误用）**：depth 注入改变的是**行为倾向**（格式、长度、口吻、禁词），**不改变事实知识**。想让模型稳定「不知道某事」，写末尾不可靠，必须进常驻描述。**「事实放常驻，行为放末尾」**是这套编排最有价值的经验规则。

### 2.3 World Info 触发机制全表【规范原文】

整理自 [3]。这是酒馆最复杂、也最值得偷的子系统。

| 机制 | 语义 |
|---|---|
| `keys` | 主关键词，默认**大小写不敏感**（可全开）；纯文本键**不支持逗号**（逗号是分隔符） |
| **Regex 键** | 键若是合法 JS 正则（`/.../flags`）则按正则匹配，可匹配动态表述与可选词 |
| `secondary_keys`+`selective` | 主键命中**且**满足二级键逻辑（UI 叫 Optional Filter）；逻辑有 **AND ANY / AND ALL / NOT ANY / NOT ALL**，NOT ANY＝「主键在但这些词都不在」，可做排他 |
| `constant`（🔵） | 无需关键词，**永远插入**（受预算限制）＝常驻层 |
| `probability` | 命中后仍按百分比掷骰决定是否插入——做随机事件、随机语气的核心 |
| `inclusion_group`+Group Weight | 同组同时命中**只插一条**，按权重随机——天然解决「多个相似提醒互斥」 |
| Prioritize Inclusion | 改为确定性：同组取 `order` 最大者，可做 fallback 序列；Use Group Scoring 则先按「命中键数量」筛出更具体子集再随机 |
| `insertion_order` | 数值越大 → 越靠上下文末尾 → **影响越大**（原文明确） |
| `insertion_position` | before/after char defs、before/after examples、Top/Bottom of AN、`@D`、**Outlet** |
| **Outlet** + `{{outlet::Name}}` | 条目**不自动注入**，内容存进命名出口，由 prompt 里的宏决定落点 ⭐ 对本项目最关键 |
| `scan_depth` | 扫描最近多少条历史找键；0＝只算递归与 A/N |
| `context%` / `budget` | WI 总可用 token；**耗尽后即便键命中也不再激活** |
| `min_activations` / `max_depth` | 忽略 scan_depth 一路回溯凑够 N 条 / 回溯上限（与 Max Recursion Steps 互斥） |
| `recursive_scanning` + Recursion Level | 条目内容提到别的条目的键→链式激活；可分层渐进披露；`max_recursion_steps` 限嵌套层数（1＝关闭） |

**预算优先序（原文）**：① constant 先插 → ② 再按 `order` 大者优先 → ③ **直接命中键的条目优先于被递归带出的条目**。

### 2.4 常驻 vs 动态召回

| 维度 | 常驻（constant） | 动态召回（keyed） |
|---|---|---|
| 预算 | 固定占用 | 按需，几乎免费 |
| 可靠性 | **必达** | 键没命中＝**静默失败**，无报错 |
| 风险 | 挤占历史；多条常驻互相稀释注意力 | 漏召回；键设计脆弱 |
| 适合 | 「缺了它回复就必错」的规则 | 长尾见闻、特定情境才需要的事实 |**准则**【个人经验】：只有「缺了它这次回复就必然错」才配常驻，其余一律 keyed。**常驻条目彼此是竞争关系**——每多一条，其他每条的实际影响力都下降。

**对本项目的反转**：短评论**没有多轮历史**，token 预算不紧张，「都塞进 prompt」在预算上可行。此时瓶颈从 **context budget** 变成 **attention dilution**：塞得越多每条越弱，且诱发「均衡满足所有要求」的平庸输出。所以正确形态是：**少而硬的常驻（≤3 条）+ 按需召回的经历**。

## 3. 社区让角色「活」的手法

> 证据以【社区共识】【个人经验】为主；官方文档只确认「机制存在」，不确认「这样写更好」。| # | 手法 | 一句话做法 | 为什么有效 |
|---|---|---|---|
| 1 | **分层 lorebook** | 世界层（不可变规则）/角色层（性格口吻）/关系层（我和你的历史）/日常层（今天心情、琐事） | 把「稳定的」与「易变的」分开：稳定层常驻复用，易变层可频繁刷新而**不污染人设** |
| 2 | **示例少而精** | 2–4 组，每组 2–3 轮，只示范语气与句式，不示范剧情 | few-shot 让模型模仿**形态**；示例一多就被当模板复读剧情 |
| 3 | **给缺点与矛盾** | 一个会让他做错事的执念 + 一个他不承认的弱点 | 完美人格没有「选择」，没有选择就没有戏；矛盾产生张力而非套话 |
| 4 | **写「当下」不只是「通常」** | 现在几点、刚发生什么、此刻心情 | 人设是常量、状态是变量；只有常量时每次输出趋同 |
| 5 | **不完美记忆** | 记错名字、记混细节、回避某些话题 | 完美记忆是数据库特征；有损、有偏好才像人脑 |
| 6 | **口头禅 + 句长硬约束** | 句长上限、必用口癖、标点习惯 | 句长与高频词是最可量化的「作者指纹」，比「性格温柔」约束强得多 |
| 7 | **禁词优于正向形容词** | 列黑名单并给替代写法 | 负向约束可执行可验证；「自然」无法被定位为具体行为 |
| 8 | **persona drift 校准** | 每 N 轮用 depth 注入重申 3 条核心特征 | 角色会**模仿自己前面的话**导致漂移，需外部锚点拉回 |
| 9 | **「是谁」与「怎么写」分离** | `description` 只写身份；`system_prompt` 只写写作纪律 | 混在一起会互相稀释；分开后可独立调参与版本化 |
| 10 | **随机化对抗千篇一律** | 同一情境备 3–5 个等价提醒，用 probability / inclusion group 掷骰 | 最被低估：**多样性是配置出来的** |

## 5. 反 AI 味规则清单（写作侧，可操作）

> 判据：AI 味的本质是**「分布均匀」**——句长均匀、信息密度均匀、立场均匀、风险均匀。所有规则都可归约为「主动制造不均匀」。【个人经验】，与 §3 社区共识一致。

| AI 味特征 | 删什么 | 换成什么 |
|---|---|---|
| 三项排比（「是…是…也是…」） | 删到剩**一项** | 只留最具体那一项 |
| 「不仅…而且…」「既…又…」 | 整个关联结构删掉 | 两个短句，或只留一半 |
| 「总之 / 综上 / 总而言之」 | 全删 | 直接结束，或落到具体细节 |
| 形容词叠用（「美丽而神秘的」） | 删形容词 | 换一个**具体名词或动作** |
| 万能过渡（「值得一提的是」「不得不说」） | 全删 | 直接说事 |
| 「不是 A，而是 B」连用 | 全文最多 1 次 | 改成陈述 B |
| 结尾 emoji / 表情三连 | 删 | 靠文字带情绪；确需则**限 1 个**且有具体语义 |
| 自我指称（「作为一个…」）／客服腔（「希望对你有帮助」） | 删 | 直接给判断 |
| 抽象大词（「独特的魅力」「时代的缩影」） | 删 | 换可验证的具体事实/数字 |
| 句句完整主谓、长度一致 | 允许省略句、口语碎片 | 主动插一个 **3–5 字短句** |
| 无立场、两头都对 | 删掉平衡表述 | 给**明确偏好或明确反对** |
| 编号/分点列表；感叹号密集 | 禁用（评论场景）；叹号限 1 个 | 连成一句话；强度交给用词 |

**【个人经验】执行建议**：把上表压成 **8–12 条可扫读短句**放进末尾注入位（见 6.3），不要放开头 system——它们都是「格式/行为」约束，正是 depth 注入擅长的（§2.2）。**条目不要超过 12 条**：一多，每条约束力就退化。

## 6. 可迁移性结论（最重要）

**场景约束（决定几乎一切）**：输出是 **B站公开短评论 10–100 字**；**单轮**，没有「下一轮可纠正」；**无对话上下文**，写评论时看不到「之前的我」；**不可撤回**；**有平台红线**（政治/色情/引战/广告/人身攻击）。

判定口径：**可用**＝机制可照搬；**改造后可用**＝语义保留、载体要换；**不适用**＝依赖多轮/角色扮演假设，硬搬负收益。

### 6.1 角色卡字段 → 「评论区人格」

| 字段 | 判定 | 理由 / 怎么改 |
|---|---|---|
| `name` | **可用** | 需要稳定自我标识（也用于去重与版本化），但不一定进 prompt |
| `description` | **可用（必须压缩）** | 真正需要的是「**身份 / 口吻 / 品味 / 红线**」，100–200 字足够。原文说它「always included」——正合我们：必须常驻 |
| `personality` | **改造后可用** | 性格形容词在单轮里无效（无行为可展现）。改成**口吻参数**：句长上限、必用/禁用词、标点习惯、梗类型 |
| `scenario` | **不适用** | 扮演的「场景」需多轮才成立。**可退化为「当前这条视频的上下文」**，由候选视频动态注入 |
| `first_mes` | **不适用（但教训极重要）** | 无开场白。但原文说 first message 是**最强风格与长度锚点**，胜过任何字段。推论：**把最想被模仿的那条评论样例放在对模型最强的位置**（prompt 末尾附近），而不是长描述中间 |
| `mes_example` | **改造后可用** | 变成**示例库 + 按形态轮换**（6.4） |
| `system_prompt` | **可用** | 放**写作纪律 + 平台红线**，与「我是谁」分离（§3#9） |
| `post_history_instructions` | **改造后可用** | 它的**位置**（最末）正是「写评论前最后一公里」的天然落点（6.3） |
| `alternate_greetings` | **不适用** | 无开场白。但「多备选 + 随机抽一」可迁到示例库与提醒库（§3#10） |
| `character_book` | **改造后可用** | 见 6.2，成败取决于召回时机 |
| `creator_notes` / `tags` / `creator` / `version` / `extensions` | **不适用（作为 prompt）** | 原文 MUST NOT 进 prompt。但**作为我们自己的元数据**完全合理——恰好印证「给人看的」与「给模型看的」要分两套存储 |

### 6.2 World Info / lorebook → 见闻库、私人经历库

**判定：改造后可用，但不能照搬编译期注入。**

**决定性事实**：本项目**候选视频在 prompt 构建之后才出现**。而 WI 的全部机制（keys、scan_depth、recursion、budget）都发生在**prompt 构建期**，只能匹配「已在上下文里的文本」。

**【规范原文】极关键的旁证**：官方文档说 **Outlet 宏在角色卡字段里无法展开**，因为那些字段「**被提前解析**，以便作为 World Info 的**额外匹配源**」。即：**任何需要「先看到内容才知道要不要用」的信息，都无法在编译期注入，只能在生成期取用。**

这正是我们的处境：见闻条目要不要用，取决于候选视频是什么，而候选视频是构建后才有的。

**正确形态＝「索引 + 按需读取」两阶段，而非编译期检索**：

1. **阶段一（索引）**：只注入**极简索引**——经历库条目标题 + 触发词（10–20 条，每条 ≤10 字），外加候选视频元信息（标题/UP/分区/热词）。
2. **阶段二（取用）**：模型先生成**取用声明**（等价于 `{{outlet::}}` 的「由调用方决定落点」），我们再注入对应条目**正文**，然后才真正写评论。**落点**：放「After Char Defs」或 `@depth` 位（影响更强侧），不放开头。

**保留的 WI 语义**：`keys`→索引触发词；`inclusion_group`/`probability`→多条经历竞争时随机挑一条（避免每条视频都讲同一个故事）；`budget`→每次最多取 2–3 条。
**必须放弃的**：`scan_depth`（无历史可扫）、`recursion`（单轮无可递归）、`constant`（见闻常驻会彻底稀释人格）。

**分层建议**（借 §3#1）：**L1 稳定偏好**（我爱/我讨厌什么）常驻 ≤50 字；**L2 具体经历**按需取用；**L3 这条视频的即时事实**每次动态注入。

### 6.3 Author's Note / depth 注入 → 「最后一公里的 3 行硬提醒」

**判定：可用，而且最值得照搬。**

- 载体换掉：我们没有「chat history depth」，但有**消息顺序**。等价做法：把最硬的 3 行约束作为**最后一条消息**（user 或 system role）放在生成点之前——即 depth 0 的语义。- 【规范原文】依据：A/N「越靠 prompt 底部影响越大」，且 `@D` 支持选 role。**用 user 角色**注入会让提醒像「用户刚提出的要求」，服从度高于同文的 system 指令。
- 内容（**恰好 3 行**）：① 形态/长度：`就这条视频说一句话，20–60 字，不复述标题。` ② 本轮的具体角度或情绪（来自候选视频 + 抽中的经历）③ 红线：`不碰政治/色情/引战/人身攻击；不写广告；不冒充 UP 本人。`
- **为什么只能 3 行**：§2.4 结论——末尾注入位是**竞争性资源**，行数越多每条越弱；3 行是「还能被逐条遵守」的上限【个人经验】。
- **不要**把事实性内容（「这 UP 我不熟」）放这里：末尾只改行为、不改知识（§2.2）。

### 6.4 示例对话 → 示例库 + 按形态轮换

**判定：改造后可用。**

- 把 `mes_example` 的「多轮对话」降维成**单条评论样例**，按形态打标签轮换：`吐槽 / 共鸣 / 提问 / 冷知识补充 / 短梗 / 反讽`。
- 每次**只注入 1–2 条**，且与本次抽中形态一致——直接对应原文「示例块逐块挤出」+「first message 是最强风格锚点」：**示例少、位置靠后，模仿效果反而更强**。
- **副产品**：形态轮换本身就是**反重复**机制。上一轮用过的形态本轮排除（§3#10）。
- **不要给 5 条以上**：模型会把示例当模板复读，评论区会被人看出是同一个号在批量发。

### 6.5 多轮记忆 / 关系状态 → 单轮下退化成什么

| 原机制 | 判定 | 单轮下的退化形态 |
|---|---|---|
| 对话历史记忆 | **不适用** | 无历史可记。**但**需要「我最近发过什么」——不是给模型看的上下文，而是**负向约束清单** |
| **跨轮自我重复** | **需新建（最重要）** | 单轮最大风险不是「忘事」而是**「每次都同一句」**。维护最近 N 条已发评论，抽 1–2 条作「禁止雷同」注入末尾位，并排除最近用过的形态与开头句式 |
| 关系状态 / 好感度 | **不适用** | **可近似为「我对这个 UP 的熟悉度」**：陌生/看过几期/老观众——影响口气亲疏与敢不敢开玩笑，静态变量 |
| 最近状态（心情/在场） | **改造后可用** | 每轮更新「最近在看什么、什么心情」，常驻 ≤30 字，让同一人格**跨天不重复** |
| persona drift 校准 | **改造后可用（反向）** | 多轮里 drift 是「人设跑偏」需拉回；单轮里是「输出同质化」需**拉开**。手段相同，目标相反 |

### 6.6 一句话总结 + 最小可用 schema

**能偷的三样**：① 「事实放常驻、行为放末尾」的位置纪律；② 「索引 + 按需取用」两阶段召回；③ 「用随机化与形态轮换制造多样性」。
**偷不来的**：多轮关系、场景扮演、开场白、记忆积累——都依赖「有下一轮」。

最小可用「评论区人格」结构【个人经验，建议落地形态】：**identity**（≤150 字：我是谁、我的品味、我的偏见）→ 常驻；**voice**（≤80 字：句长上限、口癖、标点、禁词）→ 常驻；**redlines**（≤60 字：平台红线 + 人格红线）→ 常驻，末尾再短促重申；**experience[]**（索引 10–20 条 + 正文按需取）→ 两阶段召回；**examples{}**（按形态分组的单条样例，1–2 条/次）→ 动态；**last_comments[]**（最近 N 条已发，负向约束）→ 末尾注入；**hot_state**（≤30 字：最近在看什么/什么心情）→ 常驻逐轮更新；**final_note**（3 行：形态长度 + 本轮角度 + 红线）→ 最后一条消息（depth 0）。
